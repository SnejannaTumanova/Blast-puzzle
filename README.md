# Blast Puzzle Prototype (Cocos Creator)

Игровой прототип в жанре **Blast Puzzle**, реализованный на **TypeScript + Cocos Creator 2.4.10**.

Проект демонстрирует реализацию blast-механики, каскадной обработки специальных тайлов, системы бустеров, прогрессии уровней и архитектуры с разделением ответственности.

## 🎮 Core Gameplay

Игра представляет собой классическую головоломку с blast-механикой:

- игровое поле размером **8×8**;
- каждый тайл имеет один из 5 цветов;
- при клике на тайл сжигается группа прилегающих тайлов того же цвета;
- минимальный размер группы для сжигания — **2**.

После сжигания:

- тайлы падают вниз;
- пустые ячейки сверху заполняются новыми тайлами.

## 🎯 Goal

Цель игрока — набрать необходимое количество очков за ограниченное число ходов.

### Победа

- достигнуто или превышено целевое количество очков уровня.

### Поражение

- закончились ходы;
- на поле отсутствуют доступные ходы.

## 🧩 Levels and Progression

В игре реализована система из **5 уровней**.

С каждым следующим уровнем:

- уменьшается количество доступных ходов;
- увеличивается требуемое количество очков.

Текущий уровень сохраняется локально.

После прохождения всех 5 уровней игрок может начать игру заново через кнопку **PLAY AGAIN**.

## 🎲 Playable Start State

При старте уровня поле генерируется так, чтобы в нём гарантированно существовал хотя бы один доступный ход.

Для этого после генерации используется `MoveFinder`, и если валидный ход не найден, поле пересоздаётся повторно до заданного лимита попыток.

Это позволяет избежать неиграбельного стартового состояния.

## 💣 Boosters

В игре реализованы два бустера.

### 🔁 Teleport (Swap)

Позволяет поменять местами любые две клетки на поле.

### 💥 Bomb

Уничтожает все тайлы в квадратной области **5×5** вокруг выбранной клетки.

### Ограничения бустеров

На одну игровую сессию из 5 уровней игроку доступно:

- **5** использований Swap;
- **3** использования Bomb.

Если использовать бустеры на ранних уровнях, поздние уровни становятся заметно сложнее, что поощряет стратегическое принятие решений.

### Важные правила

- использование любого бустера считается ходом;
- количество оставшихся бустеров сохраняется между уровнями;
- бустеры не сбрасываются между уровнями;
- бустеры сбрасываются только после завершения всех 5 уровней и нажатия **PLAY AGAIN**.

### Важная деталь

Бустер **Bomb** не создаёт специальные тайлы, даже если уничтожает большую группу клеток.

## ✨ Special Tiles

Если за один ход сжигается группа размером **7 и более тайлов**, на позиции исходного клика может появиться специальный тайл.

Тип специального тайла выбирается случайно из трёх вариантов:

- **Bomb** — уничтожает тайлы в зоне **3×3**;
- **RocketH** — уничтожает всю строку;
- **RocketV** — уничтожает весь столбец.

### Важное ограничение

Специальные тайлы не участвуют в обычном поиске цветовой группы и активируются отдельно — по клику или через каскадное попадание в зону действия другого спецтайла.

Во время каскадной активации новые специальные тайлы не создаются, чтобы исключить бесконечные цепочки генерации.

## 🔗 Cascade Resolution

Цепные реакции специальных тайлов реализованы через **итеративный обход очереди**, а не через рекурсию.

Алгоритм работы:

- в очередь помещается стартовый специальный тайл;
- для каждого специального тайла определяется зона действия через соответствующее поведение (`BombBehavior`, `RocketHBehavior`, `RocketVBehavior`);
- если в зоне действия находятся другие специальные тайлы, они также добавляются в очередь;
- итоговый набор клеток собирается в множество без дублей.

Такой подход:

- исключает проблемы глубокой рекурсии;
- делает каскады предсказуемыми;
- упрощает расширение системы новыми типами спецтайлов.

## 🔄 Turn Pipeline

Игровой ход обрабатывается через единый пайплайн в `GameController`.

### Обычный ход

1. Игрок кликает по тайлу.
2. `MatchFinder` ищет связанную группу соседних тайлов того же цвета.
3. Если размер группы меньше минимального порога, ход не выполняется.
4. Если группа валидна, запускается анимация удаления (`playBurn`).
5. После анимации `FieldModel.applyBurn(...)`:
   - удаляет тайлы группы;
   - при необходимости создаёт специальный тайл на месте клика;
   - схлопывает тайлы вниз;
   - заполняет пустые клетки новыми тайлами сверху.

6. Поле синхронизируется с представлением через `applyModelAnimated(...)`.
7. После завершения анимации:
   - списывается 1 ход;
   - начисляются очки;
   - обновляется HUD;
   - выполняется проверка окончания игры.

### Ход через специальный тайл

1. Игрок кликает по специальному тайлу.
2. `SpecialCascadeResolver` итеративно обходит цепочку спецтайлов через очередь.
3. Собирается итоговый набор клеток для сжигания.
4. Запускается тот же общий пайплайн `performBurnMove(...)`.
5. При каскадной активации новые спецтайлы не создаются.

### Ход через бустер

Бустеры используют отдельные action-классы, но в итоге также сводятся к общему игровому пайплайну.

#### BombBoosterAction

- выбирает область поражения радиусом 2 клетки (**5×5**);
- уменьшает число доступных бомб;
- запускает burn без создания специальных тайлов.

#### SwapBoosterAction

- позволяет выбрать две клетки;
- меняет их местами;
- проигрывает анимацию перестановки;
- списывает 1 ход;
- запускает проверку окончания игры.

## 🧠 Main Algorithms

В проекте реализованы следующие алгоритмы:

- **поиск группы тайлов** — flood fill / DFS-style traversal по соседним клеткам;
- **проверка доступных ходов** — через `MoveFinder`;
- **гравитация тайлов** — последовательный проход по колонкам;
- **каскадные реакции** — последовательная обработка очереди событий;
- **специальные тайлы** — активация через систему поведений и реестр эффектов.

Это позволяет поддерживать расширяемую систему механик и добавлять новые типы тайлов без изменения базового пайплайна.

## 🏗 Architecture

Проект организован по слоям ответственности.

### `app`

Композиция сцены и инициализация игрового окружения.

### `config`

Конфигурация уровней и сохранение прогресса:

- текущий уровень;
- количество бустеров.

### `domain`

Чистая игровая логика:

- поле (`FieldModel`);
- тайлы (`TileModel`);
- состояние игры (`GameStateModel`);
- поиск групп и доступных ходов;
- каскадная обработка спецтайлов.

### `features`

Изолированные игровые механики:

- действия бустеров;
- поведения специальных тайлов;
- реестр спецэффектов.

### `gameplay`

Оркестрация игрового процесса:

- обработка кликов;
- выполнение хода;
- переключение режимов бустеров;
- проверка win/lose.

### `presentation`

Отображение поля, HUD, бустеров, анимаций и result overlay.

Такое разделение позволяет независимо развивать игровую логику, визуальное представление и отдельные игровые механики.

## 🧩 Engineering Decisions

### 1. Единый пайплайн хода

Обычные ходы, специальные тайлы и бустеры сводятся к общему пайплайну обработки, что уменьшает дублирование логики и упрощает поддержку.

### 2. Итеративный каскад спецтайлов

Цепные реакции реализованы через очередь, а не через рекурсию. Это делает механику устойчивой и безопасной по глубине вызовов.

### 3. Разделение логики и представления

Игровая логика (`domain`, `gameplay`) отделена от визуализации (`presentation`), поэтому механику можно изменять независимо от UI и анимаций.

### 4. Контролируемая генерация спецтайлов

Новые специальные тайлы создаются только при обычном ходе и только при выполнении порога группы. В каскаде и при bomb-бустере спавн отключён, чтобы избежать бесконечных цепочек.

### 5. Сохранение прогрессии

Текущий уровень и количество бустеров хранятся в `localStorage`, что позволяет реализовать прогрессию между уровнями без серверной части.

## ⚡ Performance Considerations

При разработке были учтены следующие аспекты производительности:

- отказ от рекурсивной обработки каскадов в пользу итерационного пайплайна;
- минимизация дублирования логики за счёт общего move pipeline;
- разделение игровой логики и визуального слоя;
- возможность масштабирования механик без изменения ядра игры.
